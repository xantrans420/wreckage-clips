It's a loop, not a pipeline

Rev 1 drew a line: ad → lead → call → booked. A line has no way of finding out that the agent's answer was bad, or that it replied a second and a half too late. Four feedback paths turn it into a system that gets better instead of one that just runs.

01 — The shape

Four loops, running at four different clock speeds

The forward path along the bottom is the pipeline from rev 1 — it still exists, it's just no longer the whole picture. Every return path is a decision the system makes about itself. They nest: the further left an arrow reaches back, the more fundamental the thing it changes.

L1 — the turnmilliseconds

Does it feel like talking to someone?

Runs ~20 times per call. Governs whether the agent talks over people, leaves dead air, or answers before they've finished the sentence. This is where "laggy" lives, and it is almost entirely a configuration problem — see below.

L2 — the contacthours to days

Did we reach them at all?

No answer at 2pm → retry at 3pm → still nothing → send the SMS instead → still nothing → stop. Already in rev 1 as the retry ladder. It's a loop, but a dumb one: it doesn't learn, it just persists. Fine. Not every loop needs to be clever.

L3 — the tuningweekly

Was the agent any good?

This is the loop you were asking for. Transcripts and recordings come back, you find where the agent lost the room, and you change the prompt, the voice, the model tier, or the script. Missing from rev 1 entirely.

L4 — the targetingweekly

Were these the right people?

Booked meetings get pushed back to LinkedIn's Conversions API, so the ad optimises toward people who book rather than people who fill in forms. The slowest loop and the one with the largest financial swing, because it moves the ad spend.

02 — L1

"Maybe it's laggy" — here's exactly where the delay comes from

Response latency isn't one number, it's five stacked ones, and they are not equally fixable. A default setup lands near a full second of silence after the caller stops speaking, which reads as slow to a human ear. Under ~800 ms feels like conversation; over ~1200 ms feels broken, and people start saying "hello? hello?"

ComponentWhat it isThe fix
endpointing Deciding the caller has actually finished speaking, rather than pausing mid-sentence. The single biggest win. Drop the silence threshold to 300–500 ms and enable barge-in so the caller can cut the agent off. Too aggressive and it interrupts people; tune it against real recordings, not in the abstract.
model reply Time to the first token of the answer. Shorten the system prompt — it is re-processed every turn. Turn on prompt caching. Move heavy lookups (CRM, calendar availability) into tools the agent calls only when needed, instead of stuffing them into context. Drop to a faster model tier for the qualifying turns and keep the smart one for objections.
text → speech Time to the first audible syllable. Stream audio rather than waiting for the full sentence. Most platforms do this by default; verify yours actually is.
speech → text Finalising the transcript of what was said. Little room to move, and not worth your attention. Accented or non-native speech costs you accuracy here, not milliseconds — that's an L3 problem.
network Telephony hops between the caller, Twilio and the agent. Host the agent in the region you're calling into. A US agent dialling Latvia pays for the Atlantic twice per turn.

One caveat on "just make it faster." Sub-500 ms replies stop feeling human and start feeling like an IVR menu — real people take a beat before answering a question about budget. Latency is a range to land in, not a number to minimise.

03 — L3

"Maybe the agent's reply is shit" — how you find out, and what you turn

A bad reply is not one failure mode, it's five, and they have completely different fixes. Guessing which one you have is how teams end up rewriting a prompt for three weeks to solve a problem that was actually a wrong-language routing bug. Read ten transcripts a week and classify:

Symptom in the transcriptActual causeWhat you change
doesn't know Asked something true about your product that the agent had no information about. Knowledge base, not prompt. Add the fact and a "if you don't know, say so and offer a human" fallback.
made it up Answered confidently and wrongly — pricing, timelines, capabilities. Most damaging failure on the list. Constrain hard: the agent quotes nothing that isn't in the knowledge base. Lower temperature. This is a trust problem, treat it as urgent.
missed the objection Caller raised a real hesitation ("we already use X") and the agent ploughed on with the script. Prompt. Collect the actual objections from real calls and write handling for the top five. This is the highest-yield weekly edit you'll make.
wrong language Global targeting, and the agent opened in English to someone who wasn't comfortable in it. Route by phone country code before dialling. If you can't serve that language well, send SMS instead — a bad call is worse than no call.
talked too much Call ran 6 minutes when it should have run 45 seconds. Prompt: cap the qualifying questions, book the meeting, get off the phone. Also cuts your per-minute bill, since you're billed on wall-clock conversation time.

The weekly review, as an actual procedure

  1. Pull the week's calls sorted by outcome. Read every lost one and three booked ones — you need to know what working sounds like, not just what broken sounds like.
  2. Tag each failure with one of the five rows above. Five minutes of tagging beats an hour of impressions.
  3. Change one thing. The temptation is to fix all five at once; then your booking rate moves and you have no idea which edit did it. One change per cycle.
  4. Keep the old version. Version the prompt in git alongside the workflow. Voice agent prompts regress in ways that are invisible until a call goes badly.
  5. Re-run the failures. Keep 15–20 transcripts of calls that went wrong and replay them against the new prompt before it goes near a real lead. This is the cheapest test in the whole system and almost nobody builds it.

At 50 leads a month you cannot A/B test. Roughly 30 calls a month means a booking-rate difference has to be enormous before it's distinguishable from luck. So don't pretend: judge changes by reading transcripts, not by watching the conversion number wobble. Statistical testing becomes real somewhere north of 300 leads a month.

04 — Instrumentation

You can't loop on what you didn't log

Every loop above is powered by fields on the Airtable row. If they aren't captured at the time, the loop silently degrades into guessing — and you won't notice, because guessing feels like reviewing. Rev 1 logged the transcript and the outcome. That is not enough.

4loops
~400 msrecoverable lag
10transcripts / week
1change per cycle
  • turn_latency_p50 / p90 — per call, not per month. Averages hide the one call that took four seconds.
  • interruptions — how often the caller cut the agent off. A rising count means it's talking too much or endpointing is too slow.
  • agent_talk_ratio — share of the call the agent was speaking. Above ~60% and it's lecturing, not qualifying.
  • failure_tag — the five-way classification above, filled in by hand during review. The one field you cannot automate and the one that drives everything.
  • prompt_version — stamped on every call. Without it you cannot tell whether last Tuesday's edit helped.
  • detected_language and dial_country — the mismatch between them is your language routing bug.
  • outcome — booked / not qualified / hung up / asked for human / no answer. Not a boolean. "Asked for a human" and "hung up" mean opposite things.

05 — Consequences

What this changes in the build plan

The loops aren't a phase 6 you get to later. Two of them change work already scheduled, and one adds a week:

  • Phase 2 grows. The post-call webhook has to write the full instrument panel above, not just a transcript. Cheap to do now, expensive to backfill — you cannot recover latency data from calls that already happened.
  • New: a replay harness. Half a day of work. A script that runs saved transcripts against a candidate prompt so you can see regressions before a real lead does. This is the single highest-leverage thing in the revision.
  • The weekly review is a standing commitment, roughly an hour, indefinitely. If nobody owns it, L3 doesn't exist and you've built the pipeline from rev 1 with extra logging. Worth being honest about that before starting: the loop is a person plus a system, not a system.
  • L4 moves earlier. Pushing booked meetings back to LinkedIn was phase 4 in rev 1. It should be phase 2 — it needs weeks of data before it influences anything, so the clock should start as early as possible.
